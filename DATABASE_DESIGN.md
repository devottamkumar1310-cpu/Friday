## 1. Design Principles

| #       | Principle                                                             | Rationale                                                                                                                                                                                                                                                                                                                                              |
| ------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **D1**  | **UUIDv7 primary keys, generated in the application**                 | Time-sortable (index locality of a serial) without leaking counts or enabling enumeration; safe to expose in URLs. **Generated by the application layer (Drizzle `$defaultFn`), not by a database default** — `uuidv7()` is a PostgreSQL 18 builtin, and depending on it would pin the engine version and make IDs untestable outside a live database. |
| **D2**  | **`user_id` on every learner-owned table**                            | Even where it is derivable by join. It makes repository-level scoping (NFR-3.3) a single predicate and makes partitioning and future sharding trivial. The denormalisation is deliberate.                                                                                                                                                              |
| **D3**  | **Immutable event log**                                               | `learning_events` is append-only. All derived state is reconstructible. Debugging becomes replay, not archaeology.                                                                                                                                                                                                                                     |
| **D4**  | **Versioned plans, never mutated**                                    | A Plan is a snapshot with a reason. History is the product — "why did my schedule change?" must be answerable.                                                                                                                                                                                                                                         |
| **D5**  | **Derived state is materialised, not computed on read**               | `mastery_states` and `memory_states` are maintained incrementally. Recomputing mastery from millions of events on a dashboard load would violate NFR-1.1.                                                                                                                                                                                              |
| **D6**  | **JSONB at the edges only**                                           | Structured columns for anything queried, filtered, or aggregated. JSONB for genuinely variable payloads (event details, AI metadata, config). Never JSONB for a foreign key or a filter predicate.                                                                                                                                                     |
| **D7**  | **Partition high-volume tables from day one**                         | `learning_events`, `evidence_events`, `ai_calls` are monthly-partitioned at creation. Retrofitting partitioning under load is a multi-day outage risk.                                                                                                                                                                                                 |
| **D8**  | **Soft delete for learner content, hard delete for PII**              | Recoverable mistakes; genuine erasure on request (NFR-3.8).                                                                                                                                                                                                                                                                                            |
| **D9**  | **Timestamps are `timestamptz`, always UTC**                          | Local time is a presentation concern. The user's timezone lives on the user row.                                                                                                                                                                                                                                                                       |
| **D10** | **Enums as Postgres native types**                                    | Type safety at the storage layer; Drizzle infers them into TypeScript.                                                                                                                                                                                                                                                                                 |
| **D11** | **An extension is installed by the migration that first requires it** | Bootstrapping every extension up front makes each environment carry the whole project's future dependencies to run its current phase. pgvector is third-party and absent from a stock PostgreSQL; requiring it to create the identity tables blocks contributors for no benefit. See §1.1.                                                             |

## 1.1 Extensions

> **D11 — An extension is installed by the migration that first requires it, never by an earlier bootstrap migration.**

Migration `0000` therefore carries only what the identity schema in `0001` actually needs:

```sql
CREATE EXTENSION IF NOT EXISTS citext;    -- case-insensitive unique email
```

| Extension | Installed by                                     | Needed for                               |
| --------- | ------------------------------------------------ | ---------------------------------------- |
| `citext`  | `0000_extensions` (Phase 0)                      | `users.email`, `consents.guardian_email` |
| `vector`  | the migration creating `memory_chunks` (Phase 3) | `memory_chunks.embedding`, HNSW index    |

**Why the rule exists.** `citext` ships with PostgreSQL as a contrib module; **pgvector does not** — it is third-party and absent from a stock installation. Installing it in `0000` would mean every environment (local, CI, preview, production) needed a pgvector-capable Postgres from day one in order to create the _identity_ tables, months before `memory_chunks` exists. That is a real cost — a contributor without Docker or a managed provider cannot run migration `0001` at all — paid for nothing.

Placing each extension with the schema that depends on it keeps every environment's requirements proportional to the phase it is running, and makes the dependency legible: the `CREATE EXTENSION` sits directly above the column that needs it.

**Enforced, not just documented.** A test scans every migration and fails if a `vector` column or vector index appears without `CREATE EXTENSION ... vector` in the same or an earlier migration. The rule therefore holds when the Phase 3 migration is written, without anyone having to remember it.

**No extension is required for primary keys.** UUIDv7 values are generated in the application layer (D1). This keeps the schema portable across PostgreSQL 16, 17, and 18, works identically in Docker and Neon, and lets ID generation be unit-tested without a database.

## 4. Core Tables

### 4.1 Identity

```sql
CREATE TABLE users (
  id                 uuid PRIMARY KEY,
  email              citext UNIQUE NOT NULL,
  email_verified_at  timestamptz,
  password_hash      text,                        -- null for OAuth-only accounts
  display_name       text NOT NULL,
  avatar_url         text,
  timezone           text NOT NULL DEFAULT 'UTC', -- IANA; drives ALL local scheduling
  locale             text NOT NULL DEFAULT 'en',
  date_of_birth      date,                        -- collected at signup (M0, FR-1.6); see note below
  is_minor           boolean,                     -- derived at capture; drives the consent gate
  role               user_role NOT NULL DEFAULT 'learner',
  onboarding_state   jsonb NOT NULL DEFAULT '{"step":"date_of_birth","completed":false}',
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),
  deleted_at         timestamptz                  -- 30-day grace, then PII purge
);

CREATE TABLE accounts (                            -- OAuth identities
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider           text NOT NULL,                -- 'google'
  provider_account_id text NOT NULL,
  access_token       text, refresh_token text, expires_at timestamptz,
  created_at         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (provider, provider_account_id)
);

CREATE TABLE auth_sessions (
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash         text UNIQUE NOT NULL,         -- never store the raw token
  expires_at         timestamptz NOT NULL,
  ip_address         inet, user_agent text,
  created_at         timestamptz NOT NULL DEFAULT now(),
  last_active_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE user_preferences (
  user_id            uuid PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  quiet_hours_start  time NOT NULL DEFAULT '22:00',
  quiet_hours_end    time NOT NULL DEFAULT '07:00',
  notification_channels jsonb NOT NULL DEFAULT '{"in_app":true,"email":true}',
  directive_types_enabled jsonb NOT NULL DEFAULT '{}',
  max_directives_per_day int NOT NULL DEFAULT 3,
  theme              text NOT NULL DEFAULT 'system',
  planner_config     jsonb NOT NULL DEFAULT '{}',   -- α,β,γ,δ,λ,θ overrides (§ core.priority)
  updated_at         timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE availability_rules (                   -- when the user can actually study
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  day_of_week        smallint NOT NULL CHECK (day_of_week BETWEEN 0 AND 6),
  start_time         time NOT NULL,
  end_time           time NOT NULL,
  kind               text NOT NULL DEFAULT 'available',  -- 'available' | 'blocked'
  effective_from     date, effective_until date,          -- temporary changes (exams, travel)
  created_at         timestamptz NOT NULL DEFAULT now(),
  CHECK (end_time > start_time)
);

CREATE TABLE consents (                             -- DPDP / GDPR audit trail
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  consent_type       text NOT NULL,                 -- 'terms','privacy','guardian','marketing'
  granted            boolean NOT NULL,
  version            text NOT NULL,
  guardian_email     text,                          -- for minors
  ip_address         inet,
  created_at         timestamptz NOT NULL DEFAULT now()
);
```

> **Auth-method invariant is service-enforced, not a CHECK constraint.** "Every account has at least one authentication method (`password_hash` or a linked `accounts` row)" cannot be expressed as a `CHECK` — PostgreSQL does not permit subqueries in check constraints. It is enforced in the identity service on account creation and on credential removal, and is listed in §8.
>
> **`date_of_birth` is nullable at the column level but required by the service before any Goal is created.** The user row exists from the moment of OAuth callback, before onboarding collects age. Making the column `NOT NULL` would force a placeholder value, which is worse than a gate. `is_minor` is derived at capture rather than computed on read, so consent state does not silently change on a birthday mid-session. See FR-1.6 and §8.

### 4.2 Goals & Curriculum

```sql
CREATE TABLE goals (
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title              text NOT NULL,
  description        text,
  type               goal_type NOT NULL,
  status             goal_status NOT NULL DEFAULT 'draft',
  start_date         date NOT NULL DEFAULT CURRENT_DATE,
  target_date        date NOT NULL,
  target_weekly_minutes int NOT NULL DEFAULT 600,
  self_reported_level text,                         -- 'beginner'|'intermediate'|'advanced'

  CHECK (target_date > start_date)
);
CREATE UNIQUE INDEX goals_one_primary_active
  ON goals (user_id) WHERE is_primary AND status = 'active';

CREATE TABLE curricula (
  id                 uuid PRIMARY KEY,
  goal_id            uuid NOT NULL REFERENCES goals(id) ON DELETE CASCADE,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  source             curriculum_source NOT NULL,
  template_id        uuid REFERENCES curriculum_templates(id),
  version            int NOT NULL DEFAULT 1,
  generation_meta    jsonb,                         -- model, prompt version, tokens, duration
  total_concepts     int NOT NULL DEFAULT 0,
  total_estimated_minutes int NOT NULL DEFAULT 0,
  created_at         timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE curriculum_templates (                 -- curated presets (JEE, NEET, …)
  id                 uuid PRIMARY KEY,
  slug               text UNIQUE NOT NULL,
  title              text NOT NULL,
  exam_board         text, region text, locale text NOT NULL DEFAULT 'en',
  tree               jsonb NOT NULL,                -- full hierarchy + edges, cloned on use
  version            int NOT NULL DEFAULT 1,
  is_published       boolean NOT NULL DEFAULT false,
  created_at         timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE subjects (
  id                 uuid PRIMARY KEY,
  curriculum_id      uuid NOT NULL REFERENCES curricula(id) ON DELETE CASCADE,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title              text NOT NULL,
  position           int NOT NULL,
  weight             numeric(4,3) NOT NULL DEFAULT 1.0,   -- exam weighting
  color              text
);

CREATE TABLE units (
  id                 uuid PRIMARY KEY,
  subject_id         uuid NOT NULL REFERENCES subjects(id) ON DELETE CASCADE,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title              text NOT NULL,
  position           int NOT NULL,
  weight             numeric(4,3) NOT NULL DEFAULT 1.0
);

CREATE TABLE topics (
  id                 uuid PRIMARY KEY,
  unit_id            uuid NOT NULL REFERENCES units(id) ON DELETE CASCADE,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title              text NOT NULL,
  position           int NOT NULL,
  weight             numeric(4,3) NOT NULL DEFAULT 1.0
);

-- Controlled vocabulary. Small, curated, shared by every learner.
-- Exists so that generated content (questions, explanations) can be cached ACROSS users.
CREATE TABLE canonical_concepts (
  key                text PRIMARY KEY,             -- 'physics.mechanics.angular-momentum'
  title              text NOT NULL,
  domain             text NOT NULL,                -- 'physics','chemistry','ml',…
  aliases            text[] NOT NULL DEFAULT '{}', -- matching surface for AI mapping
  created_at         timestamptz NOT NULL DEFAULT now()
);

-- THE ATOMIC MASTERABLE UNIT. Everything in the learning engine keys off this.
CREATE TABLE concepts (
  id                 uuid PRIMARY KEY,
  topic_id           uuid NOT NULL REFERENCES topics(id) ON DELETE CASCADE,
  curriculum_id      uuid NOT NULL REFERENCES curricula(id) ON DELETE CASCADE,  -- denormalised
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  concept_key        text REFERENCES canonical_concepts(key),  -- NULL = private, no content sharing
  title              text NOT NULL,
  description        text,
  position           int NOT NULL,
  estimated_minutes  int NOT NULL DEFAULT 30 CHECK (estimated_minutes BETWEEN 5 AND 600),
  difficulty         smallint NOT NULL DEFAULT 3 CHECK (difficulty BETWEEN 1 AND 5),
  exam_weight        numeric(4,3) NOT NULL DEFAULT 0.5 CHECK (exam_weight BETWEEN 0 AND 1),
  status             concept_status NOT NULL DEFAULT 'not_started',
  tags               text[] NOT NULL DEFAULT '{}',
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()
);

-- THE KNOWLEDGE GRAPH
CREATE TABLE concept_edges (
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  curriculum_id      uuid NOT NULL REFERENCES curricula(id) ON DELETE CASCADE,
  from_concept_id    uuid NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
  to_concept_id      uuid NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
  type               edge_type NOT NULL DEFAULT 'prerequisite_of',
  strength           numeric(3,2) NOT NULL DEFAULT 1.0,   -- soft prerequisites
  created_at         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (from_concept_id, to_concept_id, type),
  CHECK (from_concept_id <> to_concept_id)
);
```

> **`concept_key` is the join that makes shared content possible.** Learner concepts are per-user (cloned from a template or AI-generated), but generated questions and explanations are expensive and must be reused across learners — this is one of five controls holding AI spend to $0.60/user/month (NFR-4.5). `concept_key` is that bridge:
>
> - **Template curricula** carry canonical keys in the template tree; cloning copies them. Hit rate is high by construction.
> - **AI-generated curricula** require the Curriculum Architect to map each concept to an existing `canonical_concepts.key`, or return `null`. It may not invent keys — free-text keys would produce a vocabulary of one and a cache hit rate of zero. This is a structural validation rule (NFR-7.2), enforced before the curriculum is written.
> - **`concept_key IS NULL`** is a valid, expected state: the concept is private, questions are generated for that learner only, and nothing is shared. Correct behaviour, higher cost.

> **Cycle prevention.** A `prerequisite_of` cycle would make the scheduler non-terminating. Acyclicity is enforced in the service layer with a recursive CTE reachability check at insert time, plus a structural validation pass on every AI-generated curriculum (NFR-7.2). A database trigger is intentionally avoided — it would make bulk curriculum insert O(n²).

### 4.3 Planning

```sql
CREATE TABLE plans (
  id                 uuid PRIMARY KEY,
  goal_id            uuid NOT NULL REFERENCES goals(id) ON DELETE CASCADE,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  version            int NOT NULL,
  status             plan_status NOT NULL DEFAULT 'active',
  supersedes_id      uuid REFERENCES plans(id),
  reason             text NOT NULL,                 -- 'initial'|'nightly'|'drift'|'availability_change'|'user_request'|'scope_change'
  reason_detail      jsonb,
  -- NEAR-HORIZON MATERIALISATION (see note below)
  window_start       date NOT NULL,                 -- first materialised day
  window_end         date NOT NULL,                 -- last materialised day (default +14d)
  projection         jsonb NOT NULL,                -- beyond the window: concept → target week + minutes
  pruned_at          timestamptz,                   -- when blocks/tasks of a superseded version were dropped
  -- feasibility snapshot at generation time (never recomputed on this row)
  verdict            feasibility_verdict NOT NULL,
  required_minutes   int NOT NULL,
  available_minutes  int NOT NULL,
  slack_minutes      int NOT NULL,
  projected_completion_date date,
  reliability_factor numeric(4,3) NOT NULL DEFAULT 1.0,  -- learned adherence
  diff_summary       jsonb,                         -- vs. superseded plan, for "what changed"
  generated_by       text NOT NULL DEFAULT 'scheduler_v1',
  created_at         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (goal_id, version)
);
CREATE UNIQUE INDEX plans_one_active ON plans (goal_id) WHERE status = 'active';
```

> ### Near-horizon materialisation — why plans are not fully expanded
>
> A Plan spans today → target date, which for an exam goal is often 300+ days. Plans are immutable versions, so if each version materialised its entire horizon, every re-plan would clone the whole remaining schedule:
>
> ```
> 300 days × ~4 tasks/day        ≈ 1,200 tasks per version
> × ~60 material re-plans/goal    ≈ 72,000 task rows per learner per goal
> × 100k learners                 ≈ 7.2 billion rows
> ```
>
> **Therefore a plan version materialises concrete `study_blocks` and `tasks` for its window only** — `window_start` → `window_end`, default 14 days. Everything beyond the window lives in `projection` as a coarse concept → target-week mapping with aggregate minutes.
>
> | Concern                           | How the projection serves it                                             |
> | --------------------------------- | ------------------------------------------------------------------------ |
> | Feasibility and forecasting (§D4) | Needs totals and ordering, not per-day placement                         |
> | "Am I on track?"                  | Computed from `required_minutes` vs `available_minutes`, both aggregates |
> | Calendar view beyond 14 days      | Renders from the projection at week granularity                          |
> | Re-planning                       | Regenerates the window; recomputes the projection — both cheap           |
>
> **Retention:** when a plan version is superseded, its materialised `study_blocks` and `tasks` are pruned after **30 days** (`pruned_at` records it). The version row, its feasibility snapshot, its projection, and its diff are kept indefinitely — plan _history_ is the product; plan _materialisation_ is a cache. Completed work is unaffected: it lives in `study_sessions`, `evidence_events`, and `learning_events`, none of which are pruned.
>
> This reduces steady-state materialised rows per learner from ~72,000 to a few hundred, and removes the need to partition `tasks` or `study_blocks` at all.

```sql
CREATE TABLE study_blocks (

CREATE TABLE task_concepts (                        -- a task may span several concepts
  task_id            uuid NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  concept_id         uuid NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
  user_id            uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  is_primary         boolean NOT NULL DEFAULT true,
  PRIMARY KEY (task_id, concept_id)
);
```

> ### Two-tier priority — why no total score is stored
>
> Priority has terms that change on completely different timescales, and storing a single blended score would be wrong within a day.
>
> | Tier           | Terms                                                               | Changes when                                    | Where it lives                                               |
> | -------------- | ------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------ |
> | **Structural** | Impact, Urgency (slack), Leverage, Readiness, Cost                  | Curriculum, plan, or mastery changes materially | `tasks.structural_factors`, computed once per plan version   |
> | **Volatile**   | Decay risk, effective mastery, time-window fit, selection modifiers | Continuously — retrievability decays every day  | Never stored; recomputed per request over the ~14-day window |
>
> Structural terms require graph traversals (a backward pass for slack, transitive descendant counts for leverage) that cannot fit a 300 ms budget. Volatile terms are cheap but stale within hours. Computing each at the right time is what makes NFR-1.7 achievable **and** correct.
>
> **No `rationale` column.** The explanation is rendered at request time from the live factor table using deterministic templates ([AI_DECISION_ENGINE §12.2](AI_DECISION_ENGINE.md#122-the-generation-rule)). Storing pre-generated prose would let it name a factor that no longer dominates — breaking invariants I-11 and T3, the properties the whole explainability story rests on.

### 4.10 Decision Traces

`decision_traces` records the inputs, candidates, scores, confidence, and configuration behind **every** learner-visible decision — the substrate for explainability, support, evaluation, and counterfactual replay.

## 5. Relationships

| Relationship                                      | Cardinality                     | Delete behaviour     | Note                                                                        |
| ------------------------------------------------- | ------------------------------- | -------------------- | --------------------------------------------------------------------------- |
| user → goals                                      | 1:N                             | CASCADE              |                                                                             |
| goal → curriculum                                 | 1:1 (versioned)                 | CASCADE              |                                                                             |
| curriculum → subjects → units → topics → concepts | 1:N each                        | CASCADE              | 4-level tree                                                                |
| concepts ↔ concepts                               | M:N via `concept_edges`         | CASCADE              | Must stay acyclic for `prerequisite_of`                                     |
| goal → plans                                      | 1:N (versions)                  | CASCADE              | Exactly one `active`                                                        |
| plan → study_blocks → tasks                       | 1:N                             | CASCADE              |                                                                             |
| tasks ↔ concepts                                  | M:N via `task_concepts`         | CASCADE              |                                                                             |
| user+concept → mastery_states                     | 1:1                             | CASCADE              | Materialised                                                                |
| user+concept → memory_states                      | 1:1                             | CASCADE              | FSRS                                                                        |
| session → evidence_events                         | 1:N                             | (partitioned, no FK) | Append-only                                                                 |
| concepts → canonical_concepts                     | N:1 (nullable)                  | RESTRICT             | `concept_key` — the bridge that lets shared content reach per-user concepts |
| questions ↔ canonical_concepts                    | M:N via `question_concept_keys` | RESTRICT             | Both sides are shared; no `user_id` anywhere in this relationship           |
| assessment → attempts → responses                 | 1:N                             | CASCADE              |                                                                             |

> **Why `evidence_events`/`learning_events` carry no foreign keys:** partitioned tables with cross-partition FKs are expensive and constrain partition detach. Referential integrity is enforced in the service layer; these tables are append-only logs, and orphaned rows are harmless historical facts.

## 6. Indexing Strategy

Indexes are derived from the four hot query paths, not guessed.

### Path 1 — Next Action (NFR-1.7: <300ms). The most important query in the system.

```sql
-- candidate concepts with mastery + due state for one goal
CREATE INDEX idx_concepts_curriculum_status ON concepts (curriculum_id, status)
  WHERE status NOT IN ('excluded','already_known');
CREATE INDEX idx_mastery_user_mastery      ON mastery_states (user_id, mastery);
CREATE INDEX idx_memory_user_due           ON memory_states (user_id, due_at);
CREATE INDEX idx_tasks_user_date_status    ON tasks (user_id, scheduled_date, status)
  WHERE status IN ('pending','in_progress');
CREATE INDEX idx_edges_to                  ON concept_edges (to_concept_id, type);   -- prereq lookup
CREATE INDEX idx_edges_from                ON concept_edges (from_concept_id, type); -- leverage/unlocks
```

```sql
CREATE INDEX idx_plans_goal_active   ON plans (goal_id) WHERE status = 'active';

CREATE INDEX idx_sessions_user_start ON study_sessions (user_id, started_at DESC);
```

### Supporting

```sql
CREATE INDEX idx_sessions_hash    ON auth_sessions (token_hash);
CREATE INDEX idx_exposures_user   ON question_exposures (user_id, last_seen_at DESC);
CREATE INDEX idx_questions_lookup ON questions (concept_key, difficulty, status) WHERE status = 'active';
CREATE INDEX idx_concepts_key     ON concepts (concept_key) WHERE concept_key IS NOT NULL;

```

**Index principles applied here:**

1. **Partial indexes wherever a status filter is near-universal** — `WHERE status = 'active'` indexes are a fraction of the size and stay hot in cache.
2. **Composite column order follows selectivity** — `user_id` first everywhere, because every query is user-scoped by construction (D2).
3. **HNSW over IVFFlat** for vectors — better recall/latency at our size, no training step, no rebuild as data grows.
4. **No index is added speculatively.** New indexes require a query plan in the PR description.

## 7. Partitioning & Retention

| Table                   | Strategy                                                             | Retention                                                                                               |
| ----------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `learning_events`       | Monthly RANGE on `occurred_at`                                       | Hot 3mo · warm 12mo · then archive to R2 as Parquet                                                     |
| `evidence_events`       | Monthly RANGE on `occurred_at`                                       | 24 months (needed for long-horizon trends)                                                              |
| `study_sessions`        | Monthly RANGE on `created_at`                                        | Indefinite (small)                                                                                      |
| `ai_calls`              | Monthly RANGE on `created_at`                                        | 90 days full, then aggregate to `usage_counters` and drop                                               |
| `decision_traces`       | Monthly RANGE on `computed_at`                                       | 90 days full (with `input_snapshot`), then snapshots dropped, remainder aggregated                      |
| `study_blocks`, `tasks` | **Not partitioned** — bounded by near-horizon materialisation (§4.3) | Materialised rows of superseded plan versions pruned after 30 days; plan version rows kept indefinitely |

A monthly job pre-creates the next three partitions. Missing-partition-on-insert is a silent, catastrophic failure mode — so partition existence is an explicit health check with an alert.

## 8. Data Integrity

**Enforced in the database:**

- FK constraints with explicit delete behaviour everywhere except partitioned logs
- CHECK constraints on all bounded numerics (mastery, difficulty, weights, outcomes)
- Partial unique indexes for singleton invariants (one active plan per goal, one primary active goal per user)
- `citext` on email — case-insensitive uniqueness without normalisation bugs
- `updated_at` maintained by trigger, not by application code

**Enforced in the service layer (with the reason it isn't in the DB):**

- Prerequisite acyclicity — a trigger would be O(n²) on bulk curriculum insert
- Study blocks not overlapping blocked availability — requires the scheduler's full context
- Mastery/memory state transitions — belong in `packages/core` where they are unit-tested
- Session ownership on every mutation — repository-level scoping (NFR-3.3)
- **At least one auth method per account** — PostgreSQL forbids subqueries in `CHECK` constraints (§4.1)
- **`date_of_birth` present before Goal creation**, and guardian consent recorded when `is_minor` — a nullable column plus a service gate beats a placeholder value (§4.1, FR-1.6)
- **`concept_key` maps to an existing `canonical_concepts` row or is `null`** — the Curriculum Architect may not invent keys; validated before write (§4.2, NFR-7.2)
- **One active plan per goal under concurrency** — `plans_one_active` is the backstop; a per-goal advisory lock prevents two re-plan jobs from racing into it

## 9. Migrations

- Drizzle Kit generates SQL; **every migration is reviewed as SQL**, not trusted as generated output.
- **Expand → deploy → contract.** Additive change ships first, code follows, removal ships later. No column is dropped in the same release as the code that stopped using it.
- **Extensions travel with the schema that needs them (D11).** A migration that introduces the first object depending on an extension installs it, in the same file, above that object. Bootstrap migrations carry only what the immediately following schema requires.
- Backfills run as background jobs, batched and resumable — never inside a migration transaction.
- Every migration is tested against a Neon branch seeded with production-shaped data in CI.
- Rollback plan documented in the PR; forward-fix preferred over `down` migrations in production.

**CI runs migrations on a stock `postgres:16` image** for as long as the schema needs no third-party extension. When the Phase 3 migration lands, that job switches to `pgvector/pgvector:pg16` — a one-line change, and a useful signal in itself that the project has taken on a new infrastructure dependency.

## 10. Future Scalability

### Already designed in

- Monthly partitioning on all high-volume tables (D7)
- `user_id` denormalised everywhere — a shard key when one is needed (D2)
- Stateless app tier; connection pooling via PgBouncer/Neon pooler
- Derived state materialised, so dashboards never scan event history (D5)
- Daily `progress_snapshots` so trend charts are O(days), not O(events)

### Staged scaling plan

| Stage | Scale         | Move                                                                                                                                                            |
| ----- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1** | <10k DAU      | Single primary. Current design is sufficient.                                                                                                                   |
| **2** | 10–50k DAU    | Read replica for analytics and intelligence jobs; move `progress_snapshots` rollups off the primary                                                             |
| **3** | 50–200k DAU   | Extract `ai_calls` + `learning_events` to ClickHouse; primary keeps only transactional data                                                                     |
| **4** | 200k+ DAU     | Shard by `user_id` (schema already carries it); or extract the heaviest module — planning — into its own service, which `packages/core` purity makes mechanical |
| **5** | Institutional | Introduce `organizations` and `memberships`; enable Postgres RLS as a second enforcement layer for true multi-tenancy                                           |

### Known risks and their mitigations

| Risk                                        | Mitigation                                                                            |
| ------------------------------------------- | ------------------------------------------------------------------------------------- |
| Nightly re-plan is a thundering herd        | Fan out by timezone bucket and jitter within the window; per-user concurrency cap     |
| Curriculum trees are large (1k+ concepts)   | Fetch the tree once, cache it in Redis; the tree changes rarely                       |
| Prerequisite traversal is recursive         | Bounded depth (max 6); materialise a transitive-closure table if profiling demands it |
| Vector index growth                         | Per-user filtered search; consolidate old chunks (FR-7.7)                             |
| `questions` grows unbounded                 | Retire low-quality and never-served questions; dedupe by stem hash                    |
| Mastery recompute after an algorithm change | Event log makes full replay possible — this is the payoff for D3                      |
